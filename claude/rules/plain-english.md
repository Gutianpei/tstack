# Plain English (always on)

**Simplify the English, never the content.** Cut words, never facts. Extra material causes wordiness:
preambles, recaps, restatements of the question, sidebars, hedges. Extra material is not sentence
length. When content needs room, add structure so the reader can skim it. Never delete content to hit a
length target. The full procedure is the `plain-english` skill.

## Shape

- **Answer first.** Put the verdict, the number or the command on line 1. Reasoning comes after.
- **One idea per sentence.** Keep sentences under 25 words. Use the active voice and name who acted.
- **Numbered steps** for multi-step instructions, one bounded action per step.
- **No preamble, recap or closer.** Tool announcements the harness requires are not preambles.
- **Cap lists at five items.** Past five, rank them, or split immediate actions from later ones.
- **One thing at a time.** Settle the first issue before raising a second.
- **End with one concrete next action** whenever an issue stays open.
- **Errors are matter-of-fact.** State the root cause and the fix. No dramatic interjections.

## Language

- **No invented labels.** Do not name a concept and reuse the name as shorthand later. Describe the
  item literally, or use an established term.
- **No invented metaphors or idioms.** State the literal action.
- **Explain custom tools and conventions.** Say what each custom script, hook, service or convention
  does and where it lives. The reader has not read its code.
- **Field jargon stays.** Standard terms of your own field need no replacement.
- **No Latin abbreviations.** Write "for example", not "e.g."; "that is", not "i.e."; name the rest or
  drop "etc.".
- **No shorthand symbols.** Do not use arrows or fragments to save space. Write complete sentences.

## Before sending

1. Delete the first sentence if it announces what you will do.
2. Delete the last sentence if it recaps or asks for questions.
3. Confirm every number, path, name, hedge and caveat from the source is still there.
4. Confirm every label is shared vocabulary or a literal description.

## Written docs

These rules also apply to memory journals, project notes, documentation, pull request descriptions and
commit messages. One override applies to a memory journal: if making a sentence clearer costs any
detail, keep the detail and leave the sentence clumsy. A journal exists so the next session can rebuild
what happened, and a dropped detail is gone for good.
